1. Executive Summary & Problem Formulation

SignBridge is a production-ready, full-stack American Sign Language (ASL) learning, translation, and gamified practice ecosystem. The platform bridges the communication divide between the Deaf and Hard of Hearing (DHH) community and the hearing population, directly supporting United Nations Sustainable Development Goal 10 (Reduced Inequalities).

Traditional sign language translation systems suffer from three primary bottlenecks:

  1. Hardware Dependency: Requiring costly wearable sensory gloves or multi-depth cameras.
  2. High Latency & Cloud Transmission: Streaming uncompressed video frames to remote cloud servers creates bandwidth bottlenecks, latency spikes, and severe visual privacy violations.
  3. Lack of Real-Time Pedagogical Guidance: Conventional machine learning classifiers act as black boxes (simply displaying predicted sign names) without providing actionable biomechanical feedback to help learners correct individual finger curls or joint angles.

The SignBridge Solution: We implement an edge-first computer vision pipeline executing directly in the client browser at 60 FPS using MediaPipe Hands. Spatial 3D coordinates are extracted on the user's device and evaluated via a deterministic biomechanical geometric classifier. Generative AI tutoring is securely proxied through an Express backend via Google Gemini 2.5 Flash, delivering real-time interactive posture corrections without exposing API credentials.

4. Computer Vision & Machine Learning Pipeline

The sign recognition system utilizes a hybrid pipeline combining deep-learning keypoint regression with deterministic biomechanical geometry.

4.1 MediaPipe Hands: Two-Stage Deep Learning Architecture

  1. BlazePalm Detector: A single-shot detector optimized for mobile and web architectures. It detects hand presence and estimates oriented bounding boxes across the entire video frame with $O(1)$ scale invariance.
  2. Hand Landmark Model: A convolutional neural network regressor operating on the cropped hand region. It predicts exact 3D coordinates for 21 key anatomical landmarks per hand:
MediaPipe 21 Hand Landmarks Map:
  [0] Wrist
  [1-4]   Thumb  : CMC(1) -> MCP(2) -> IP(3)  -> TIP(4)
  [5-8]   Index  : MCP(5) -> PIP(6) -> DIP(7) -> TIP(8)
  [9-12]  Middle : MCP(9) -> PIP(10)-> DIP(11)-> TIP(12)
  [13-16] Ring   : MCP(13)-> PIP(14)-> DIP(15)-> TIP(16)
  [17-20] Pinky  : MCP(17)-> PIP(18)-> DIP(19)-> TIP(20)

4.2 Scale and Distance Normalization (Palm Scale Invariance)

To ensure gestures are classified accurately regardless of whether a user stands close to the camera or far away, every distance is normalized by the physiological Palm Scale Factor ($S_{palm}$), defined as the Euclidean distance between the Wrist ($L_0$) and the Middle Finger Knuckle ($L_9$):

$$S_{palm} = | ec{P}_{L9} - ec{P}_{L0}| = sqrt{(x_9 - x_0)^2 + (y_9 - y_0)^2 + (z_9 - z_0)^2}$$ $$d_{normalized}(A, B) = rac{| ec{P}_A - ec{P}_B|}{S_{palm}}$$

4.3 Biomechanical 3D Joint Angle Calculation

Rather than relying solely on raw $(x,y)$ coordinates, the engine computes 3D angular flexion at Proximal Interphalangeal (PIP) and Distal Interphalangeal (DIP) joints using vector dot products:

$$ ec{u} = ec{P}_{MCP} - ec{P}_{PIP}, quad ec{v} = ec{P}_{TIP} - ec{P}_{PIP}$$ $$cos( heta) = rac{ ec{u} cdot ec{v}}{| ec{u}| | ec{v}|}, quad heta = arccosleft( ext{clamp}left(cos( heta), -1, 1 ight) ight) imes rac{180^circ}{pi}$$
  • Fully Extended Finger: $ heta in [140^circ, 180^circ]$ with normalized tip distance $ rac{| ec{P}_{TIP} - ec{P}_{Wrist}|}{S_{palm}} > 1.05$.
  • Curled Finger (Fist): $ heta < 112^circ$ or normalized tip-to-knuckle distance $< 0.50$.
  • Curved Finger (Arc): $100^circ le heta le 138^circ$ (characteristic of the letter 'C' and numbers).

4.5 Temporal Smoothing Filter (Jitter Removal)

Raw webcam landmark outputs can exhibit high-frequency frame jitter due to lighting or camera sensor noise. The HandDetectionEngine implements a temporal consensus buffer ($N = 3$ frames). A sign is only confirmed when the modal prediction frequency satisfies:

$$ ext{P}_{ ext{confirmed}} = argmax_{c} sum_{i=1}^{N} mathbb{I}(p_i = c) quad ext{subject to} quad rac{ ext{Count}(c)}{N} ge 0.66$$

5. AI Assistant (SignBot) & Google Gemini Integration

5.1 API Key Security & Architectural Boundary

Crucial Security Rule: API keys must NEVER be bundled into frontend JavaScript files where client inspection or decompilation can expose credentials.

Secure Server-Side Proxy Design Pattern

1. Backend Storage: The API key is stored exclusively inside backend/.env as GEMINI_API_KEY, loaded into memory via dotenv.
2. Client Call: The frontend client issues an HTTP POST request to /api/ai/chat containing only the user prompt and context.
3. Authenticated Dispatch: The Express controller attaches the server-side API key and calls Google's REST endpoint via secure HTTPS.
4. Sanitized Output: The response is parsed, sanitized, and returned as clean JSON to the client.

5.2 Model Selection & Graceful Fallback Cascade

SignBridge leverages Google Gemini 2.5 Flash (gemini-2.5-flash), providing state-of-the-art reasoning, sub-second latency, and native structured formatting at low computational cost.

To ensure 100% platform uptime during academic reviews or external API outages, the backend controller implements a multi-tier fallback cascade: 

Client Request
      ↓
[Tier 1] Google Gemini 2.5 Flash (Primary model: fast, nuanced ASL pedagogy)
      ↓ (if HTTP 404 or regional model restriction)
[Tier 2] Google Gemini 2.5 Flash Lite (Lightweight alternative)
      ↓ (if unavailable)
[Tier 3] Google Gemini 1.5 Flash (Legacy stable endpoint)
      ↓ (if network offline or API quota exceeded)
[Tier 4] Embedded Local Knowledge Engine (Deterministic, zero-network fallback)

5.3 Pedagogical Persona & Grounding System Prompt

SignBot is strictly grounded with a comprehensive ASL domain model. It avoids hallucinations by referencing the exact 21 supported signs in SignBridge, guiding students through finger placement, hand orientations, and common signing mistakes.

6. Gamification Engine: "Sign Rush" (Time-Attack Game)

The gamification engine combines reinforcement learning principles with speed-recognition drills to enhance learner retention:

  • Challenge Modes: 30-Second Blitz (sprint challenge) and 60-Second Marathon (endurance test).
  • Vocabulary Filtering: Dynamic selection between Alphabets & Numbers, Everyday Signs, or Full Catalog.
  • Dynamic Streak Multiplier:
    $$ ext{Points} = left( 100 + ext{RemainingTime} imes 5 ight) imes M_{ ext{streak}}$$ $$M_{ ext{streak}} = egin{cases} 1.0 imes & ext{streak} < 3 \ 1.5 imes & 3 le ext{streak} < 5 \ 2.0 imes & 5 le ext{streak} < 7 \ 3.0 imes & ext{streak} ge 7 end{cases}$$
  • Web Audio API Synthesizer: Generates synthetic sound waves (sine, triangle, and square waveforms) dynamically in real-time, requiring zero external MP3/WAV audio assets.
  • Resource Isolation: The camera and computer vision loop are mounted strictly while gameState === 'PLAYING' and torn down completely upon game completion to conserve hardware resources.

7. Comprehensive Viva Voce / Project Review Defense Q&A

Below are the most critical technical questions commonly asked by university project evaluators, along with authoritative, high-scoring responses:

Q1. Why did you choose MediaPipe Hands over training a custom CNN or YOLO model from scratch?
Answer: Training a custom Convolutional Neural Network (CNN) directly on RGB pixels introduces three major drawbacks:
1. Lighting & Skin Tone Bias: Pixel-based CNNs overfit to specific background illumination and skin pigmentation. MediaPipe abstracts the hand into 21 geometric 3D coordinate points, providing lighting and skin-tone invariance.
2. Client-Side Execution (Edge Computing): MediaPipe executes via WebAssembly/GPU acceleration directly in the user's browser at 60 FPS, eliminating costly GPU server hosting.
3. Data Privacy: Video frames never leave the user's computer, fulfilling stringent data protection standards.
Q2. How does the system handle scale, distance, and hand orientation variance?
Answer: We implement Palm-Scale Normalization. We compute the 3D Euclidean distance between the wrist ($L_0$) and the middle finger metacarpophalangeal joint ($L_9$) as the physiological base palm scale $S_{palm}$. All spatial distances between fingertips and knuckles are divided by $S_{palm}$. Furthermore, we calculate 3D joint flexion angles using vector dot products, which are mathematically scale-invariant by definition.
Q3. How is the Gemini API Key secured in your application?
Answer: We strictly follow the Server-Side Proxy Architecture. The client application has zero knowledge of the API key. The key resides inside backend/.env on the server. The client sends chat queries to our Express backend route (/api/ai/chat). The backend attaches the key in an authenticated HTTPS call to Google's API, validates the response, and forwards the response to the user.
Q4. What happens if the user's internet connection drops or the Gemini API hits a rate limit?
Answer: We engineered a 4-tier resilience fallback. If Google's endpoint returns HTTP 404, 429 (rate limit), or if network connectivity is lost, our backend automatically catches the exception and falls back to our embedded Deterministic ASL Rule Engine. This ensures the user receives an accurate, pedagogical answer without the portal crashing.
Q5. How do you prevent webcam hardware conflicts between the Translate, Practice, and Sign Rush modules?
Answer: We designed a unified CameraBox component adhering to strict React lifecycle hooks. Whenever a user navigates away or switches tabs, the useEffect cleanup function explicitly invokes stream.getTracks().forEach(track => track.stop()), releases the hardware lock, and cancels active requestAnimationFrame loops, preventing resource contention.
Q6. What is the role of the Feature Activation System in your architecture?
Answer: In academic and commercial evaluation, modularity is essential. We implemented a centralized FeatureContext with LocalStorage persistence. Advanced features like SignBot AI and the Sign Rush game are OFF by default. They can be toggled independently without affecting existing modules. When turned off, zero background CPU/memory resources are consumed.
Q7. What was the root cause of the blank white screen on the Sign Rush route, and how did you resolve it?
Answer: The white screen was caused by an uncaught ReferenceError: openSettingsModal is not defined inside SignRushActive. In React 19, an uncaught rendering exception in any component unmounts the entire root DOM tree if no Error Boundary exists. We resolved this by: (1) supplying openSettingsModal directly through useFeatures() in the active component, (2) hoisting helper functions outside the component to prevent Temporal Dead Zone errors, and (3) wrapping application routes in a custom ErrorBoundary component to display a recovery banner rather than crashing.
Q8. How does SignBridge relate to United Nations SDG 10 (Reduced Inequalities)?
Answer: SignBridge reduces educational, vocational, and social inequalities for Deaf and Hard of Hearing individuals by providing a free, browser-accessible platform that translates ASL in real-time and enables hearing peers, teachers, and employers to learn and practice sign language with objective biomechanical feedback.
